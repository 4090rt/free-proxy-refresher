# План: проверка SOCKS5 через TCP-туннель

Режим проверки на основе рукопожатия из `TestSocks5/TestSocs5.cs`, без `SocketsHttpHandler` и без TLS.
Работает независимо от HTTP-режима: в любой момент активен максимум один.

## Решения, зафиксированные при планировании

| Вопрос | Решение |
|---|---|
| Как связаны режимы | Два независимых режима, одновременно не работают |
| Глубина проверки TCP | Рукопожатие + фактический проброс данных |
| Цель CONNECT | `httpbin.org:80`, без TLS |
| Семафор | `static` `SemaphoreSlim`, по одному на режим |
| Занятый семафор | Сразу `«уже выполняется»`, без ожидания |
| Параллелизм | `MaxDegreeOfParallelism = 15` |
| Контроллер | Маршруты в существующем `ControllerGetAllProxy` |
| Окно свежести | `AbsoluteExpirationRelativeToNow = 3 ч`, без `Sliding` |

## Схема ключей кэша

```
Socks5Cache_key            ← сырой полный список      (таймер, Cache())
Socks5Cache_key_stale      ← он же, на случай протухания
Socks5Checked_key_http     ← проверено через SocketsHttpHandler
Socks5Checked_key_tcp      ← проверено через рукопожатие
```

## Зачем два ключа, а не один

Один ключ на оба режима означает, что более слабая TCP-проверка затёрла бы результат сильной HTTP-проверки. Раздельно: каждый режим пишет своё, `/SOCKS5` выбирает по свежести `CheckedAtUtc`.

## Исходная проблема: потеря прокси

Чекер обязан читать **сырой** список через `GetRaw()`, а не через `Get()`.
Если читать через `Get()`, то на втором цикле берётся собственный вывод предыдущего — фильтр поверх фильтра, и список может только уменьшаться. Прокси, отвалившийся на 5 минут, больше никогда не попадёт в проверку.

Маршруты чтения строго разведены:

- `GetRaw()` — всегда полный список из источника. Только чекер.
- `GetTestedTcp()` / `GetTestedHttp()` — только проверенное, без отката на сырой. Только контроллер.
- `Get()` — клиентский: свежайший из двух проверенных, иначе `GetRaw()`.

## Найденные проблемы в `TestSocs5.cs`

Рукопожатие написано верно: приветствие `05 01 00`, чтение 2 байт, CONNECT с ATYP `0x03`, разбор ответа по ATYP, доменное хвостовое чтение. Размеры буферов снятия с пула рассчитаны верно, 258 байт покрывают максимум `1 + 255 + 2`. Чтение 2 байт, затем 4 — не перекрытие, ответ на приветствие ровно 2 байта.

| Проблема | Место | Решение |
|---|---|---|
| Утечка сокета на успешном пути | `:74`, `:79` | `TcpClient` освобождается только в `catch`, на успехе вызывающий получает `Stream` без владения `TcpClient`. На 2000 прокси — 2000 висящих сокетов | `Socks5Tunnel : IDisposable`, владеет `TcpClient` |
| `ReceiveTimeout`/`SendTimeout` мёртвый код | `:39-40` | Весь обмен async с `ct`, сокетные таймауты не срабатывают никогда, реальный лимит задаёт `cts` | Удалить |
| `int.Parse(httpParse.Port)` | `:36` | Нечисловой порт бросает исключение и пишет стектрейс в лог | `int.TryParse`, тихий `return null` |
| Нет отмены снаружи | `:35` | `cts` создаётся внутри, цикл не может отменить обход | `CreateLinkedTokenSource(ct)` |
| Нет проверки проброса | `:74` | «Живой» = рукопожатие принято. Прокси-чёрная дыра пройдёт | Писать GET поверх туннеля, читать первую строку |
| Лог на каждый мёртвый прокси | `:78` | 2000 стектрейсов заливают лог и таблицу логов | `return false` без `ExceptionLog`, счётчики у чекера |
| Комментарий про 4 байта | `:28` | Рентится 15, написано «4 байта» | Привести в соответствие |

`TestSocs5` нигде не зарегистрирован в DI и не вызывается, `grep` не нашёл ни одной ссылки — переделка ничего не сломает.

## Шаги реализации

### 1. `TestSocks5/Socks5Tunnel.cs` (новый)

```csharp
public sealed class Socks5Tunnel : IDisposable
{
    private readonly TcpClient _client;
    public Stream Stream { get; }
    internal Socks5Tunnel(TcpClient client, Stream stream) { _client = client; Stream = stream; }
    public void Dispose() => _client.Dispose();
}
```

### 2. `TestSocks5/TestSocs5.cs`

- `Test()`: `Task<Stream?>` → `Task<Socks5Tunnel?>`, тело без изменений кроме типа возврата
- `int.TryParse(httpParse.Port, out int port)`, при `false` тихий `return null`
- `CancellationTokenSource.CreateLinkedTokenSource(ct)`, внутренний лимит 7 с
- удалить `ReceiveTimeout` / `SendTimeout`
- новый метод проверки, вся логика рядом с рукопожатием, чекер байты протокола не дублирует:

```csharp
public async Task<bool> CheckAsync(HttpParse parse, CancellationToken ct)
```

- открывает туннель в `using`
- пишет поверх туннеля `GET / HTTP/1.1` + `Host: httpbin.org` + `Connection: close`
- читает **первую строку** ответа — достаточно для доказательства проброса, тело дочитывать не нужно
- `true` только при `HTTP/1.1 200`
- без `ExceptionLog` на мёртвый прокси

### 3. `Cache/CheckedSocks5.cs` (новый)

```csharp
public class CheckedSocks5
{
    public List<HttpParse> Proxies { get; set; } = new List<HttpParse>();
    public DateTime CheckedAtUtc { get; set; }
}
```

### 4. `Cache/MemoryCacheSocks5List.cs`

- `Get()` → `GetRaw()`, тело не трогать
- приватные `TryGetChecked(string key)` и `CacheChecked(string key, List<HttpParse>)` — общая механика без дублирования
- четыре тонких обёртки: `GetTestedHttp()`, `GetTestedTcp()`, `CacheCheckedHttp(...)`, `CacheCheckedTcp(...)`
- `CacheChecked`: пустой список не писать, **без stale-пары**, **только `AbsoluteExpirationRelativeToNow = 3 ч`**, без `Sliding`
- новый клиентский `Get()`: читает оба ключа, берёт свежее `CheckedAtUtc`; оба отсутствуют → `GetRaw()`
- `LastCheckedUtc` — максимум из двух дат

`Sliding` здесь недопустим: `/SOCKS5` дёргают постоянно, скользящий срок продлил бы запись вечно при трёхдневной давности проверки. Stale-пара недопустима: иначе `GetTested*` отдаст запись, которой 11 часов.

### 5. `TestSocks5/Socks5ProxyChecker.cs` (новый)

- `Socks5CheckMode { Http, Tcp }`
- по семафору на режим: `static readonly SemaphoreSlim GateHttp` и `GateTcp`. Один общий запрещал бы две проверки сразу, а разные ключи не конфликтуют. Сообщения точнее: «TCP уже идёт» против «HTTP уже идёт»
- `WaitAsync(0, ct)` — при занятом семафоре сразу `«уже выполняется»`
- всегда читает `GetRaw()`, никогда `GetTested*`
- `MaxDegreeOfParallelism = 15`
- пишет `CacheCheckedHttp` / `CacheCheckedTcp` соответственно
- `Release()` в `finally`; при отмене частичный результат **не** сохраняем

`static` обязателен: класс регистрируется `AddScoped`, инстансных семафоров два параллельных запроса не увидят.

### 6. `Controller/ControllerGetAllProxy.cs`

| Маршрут | Действие |
|---|---|
| `/SOCKS5` | `Get()` — свежайший из двух проверенных, иначе сырой |
| `/SOCKS5RAW` | `GetRaw()` всегда |
| `/SOCKS5TCP` | `GetTestedTcp()` строго |
| `/SOCKS5HTTP` | `GetTestedHttp()` строго |
| `/SOCKS5CHECKTCP` | запуск TCP-режима |
| `/SOCKS5CHECKHTTP` | запуск HTTP-режима |

Два отдельных маршрута проверки вместо `?mode=`: раз режимы независимы и активен максимум один, параметр добавил бы неоднозначности. `/ALL` (строка 111) берёт тот же `Get()`, что и `/SOCKS5`.

### 7. `Program.cs`

`AddScoped<TestSocs5>()`, `AddScoped<TestSocksClient>()`, `AddScoped<TestSocks5WebProxy>()`, `AddScoped<Socks5ProxyChecker>()` — после строки 92, до `AddMemoryCache()` и `servise.BuildServiceProvider()` (строка 95).

### 8. Сборка и замер

`dotnet build`, затем прогон обоих режимов на одном и том же списке и сравнение: сколько прошло в каждом, сколько заняло, сколько живых в обоих одновременно. Эта таблица покажет, чего стоит TCP-режим отдельно.

## Оценка времени на 2000 прокси, параллелизм 15

| Режим | Типично | Худший случай (все по 7 с) |
|---|---|---|
| HTTP | ~2 мин | ~15 мин |
| TCP | ~40 с | ~15 мин |

Худший случай у обоих один — он упирается в 7-секундный таймаут при 15 параллельных, а не в сам подход.

## Оговорка про маршруты проверки

`/SOCKS5CHECK*` по плану `await`-ит и возвращает счётчики. Типичный TCP-цикл это ~40 секунд, худший — 15 минут. Держать HTTP-соединение открытым 15 минут рискованно, и при обрыве клиента счётчики потеряются, хотя проверка дойдёт до конца.

Сейчас оставляем `await` с возвратом счётчиков. Если 15 минут окажутся проблемой — переделка в фоновую задачу с `202 Accepted` и отдельным `/SOCKS5STATUS`. Это изменение контракта, делается только по решению.

## Порядок внедрения

TCP-режим реализуется **после** HTTP-режима: чекер общий, кэш общий, отличаются только ветка проверки и ключ записи. Порядок шагов: сначала пункты 1-4, 6-7, потом HTTP-режим, и последним TCP.
